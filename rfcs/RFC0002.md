<h1 style="text-align: center;">[RFC#0002] SiteService, Modes and Policies</h1>

# Abstract

A `SiteService` is one application name. It lists the members of a dependency across sites, picks the active ones from observations, and writes the endpoints of a local Service. This RFC fixes the resource, the two v1 modes, and the policies that decide where the name points when observations are incomplete or contradict each other.

# Overview

The operator applies the same `SiteService` at every site. Each site's controller:

1. observes its local members through the plugin ([RFC#0003]);
2. reads the peers' observations ([RFC#0004]);
3. decides the route with the rules below;
4. writes the endpoints of the application name: the member's ready pods when local, the gateway when remote ([RFC#0005]).

```yaml
apiVersion: strait.tako.id/v1
kind: SiteService
metadata:
  name: pg
  namespace: app
spec:
  mode: Single
  port:
    name: postgres
    port: 5432
  plugin:
    cnpg:
      role: primary
  members:
    - name: pg-a
      site: a
      cnpg:
        cluster: pg-a
    - name: pg-b
      site: b
      cnpg:
        cluster: pg-b
  policy:
    multiple: RouteNowhere
    unknownHold: 30s
```

# Motivation

| Observed failure or risk | Rule it gives |
|---|---|
| Two writable primaries after a partition heals. Writes to both diverge. | Two writable members route nowhere by default. |
| A switchover in progress has no writable primary for seconds. A client that connects then hangs on a read-only node. | A primary with no confirmed writable member routes nowhere, so the client is refused at once and retries. |
| Two sites whose configuration names different primaries. One of them is wrong, and Strait cannot tell which. | Disagreeing declarations always route nowhere. No policy relaxes this. |
| A peer stops answering for a few seconds during a link flap. Dropping its route at once would turn a flap into an outage. | Unknown keeps the last route for a bounded time. |
| A peer stays unreachable. The member it hosts may have moved. | After the bound, Unknown routes nowhere. |
| A partition hides one site. The local primary keeps serving the local site. | An Unknown member that is not routed does not block a confirmed writable member. |
| A site was lost while its member was primary, and the operator promoted another site's member without a token. When the site came back, still primary, its controller started and routed to its local primary before it had read the other site. For about 20 seconds, its clients could write to a primary the other site had abandoned. | An opt-in startup hold. After the controller starts, `Single` mode does not route to a local member until it has read every site with a member, or until the hold ends. |
| In a two-site test, the route moved away from a local member, which became a read-only replica. Over the next 2 hours, a client at that site opened 15 new connections straight to the old member's pod address and port. The application Service's EndpointSlice and the CNI's service map held only the gateway. | A route change rewrites the endpoints and nothing else. A client does not rely on it to stop traffic to a demoted member. See [Route changes and connections](#route-changes-and-connections). |
| In a review, a test moved the route from one member to another in one reconcile. The controller wrote the new member's EndpointSlice before it deleted the old one's, so both members were endpoints for one API round trip. With the delete failed, both stayed, and status showed the new route as `Active`. | A route change deletes before it writes, and writes nothing once a delete fails. It passes through nowhere. |
| In a review, a test dropped a moving member from the route, and failed the status write that followed. When the member's site then went stale, the member was routed again as `HeldUnknown`: the previous route came from status, which still named it. | The previous route is the last decision. After a start, it is the members of `status.route` that still have an EndpointSlice. |
| In a review, a test failed a write after the route moved away from a member. That member's EndpointSlice and the old status stayed in force, and no condition said the decision was not applied. The error also put the next decision behind the controller's backoff, so a hold could outlast `unknownHold`. | Deletes come first, and status is written after every decision, with an `Applied` condition. An error does not delay the next decision. |
| In a review, a test gave Strait's Service another owner. The EndpointSlices that Strait had written still carried the Service's name, so they kept feeding that Service with the member routed before. | On a Service conflict, the controller deletes every EndpointSlice of the `SiteService`. |
| In a two-site test, a whole site restarted. Its `SiteService` showed the route from before the restart, reason `Active`, for about 40 seconds, until the new controller first polled its peers. Nothing was routed. The `strait` CLI and a failover tool that waits on the route took that status as current. | Until the elected controller's first poll of every peer has ended, the route's reason is `AwaitingPeers`. |

# Requirements

## Resource

1. `spec.mode` MUST be `Single` or `Set`.
2. `spec.locality` MUST be one of `LocalFirst`, `LocalOnly`, `Any`, and MAY be set only in `Set` mode. When it is unset in `Set` mode, the controller MUST use `LocalFirst`.
3. `spec.port` MUST name exactly one TCP port. The application name's Service MUST expose that port and name.
4. `spec.members` MUST hold between 1 and 16 members. Each member MUST have a `name` unique in the list and a `site`.
5. `spec.plugin` MUST name exactly one plugin. Every member MUST carry the source block of that plugin and no other.
6. `spec.policy.multiple` MUST be `RouteNowhere` or `PreferDeclaredIfConsistent`. The default is `RouteNowhere`.
7. `spec.policy.unknownHold` MUST be between 0s and 10m. The default is 30s.
8. Every MUST and MUST NOT in this list MUST be enforced by the CRD's schema or validation rules, so `kubectl apply --dry-run=server` rejects a violation. Defaults that depend on the mode are applied by the controller.

## Output

9. The controller MUST write a Service named after the `SiteService`, in its namespace, with no selector, and MUST own it. If a Service of that name exists and another owner holds it, the controller MUST NOT change it, MUST report the conflict in status, and MUST delete the EndpointSlices of the application name. Checked by a unit test and by the end-to-end `conflict` step.
10. The controller MUST write the Service's endpoints as EndpointSlices labelled `kubernetes.io/service-name` and `endpointslice.kubernetes.io/managed-by: strait.tako.id`.
11. A local active member's endpoints MUST be the ready addresses of the member's endpoint Service, on that Service's target port.
12. A remote active member's endpoints MUST be the active gateway's address on the member's `Import` port, or the member's own addresses when endpoint-direct applies ([RFC#0005]).
13. To route nowhere, the controller MUST leave the Service with no endpoints.
14. A change of route MUST change only the application name's EndpointSlices. It MUST NOT close or move an established connection. New connections follow the route as the CNI resolves the Service ([Route changes and connections](#route-changes-and-connections)).

## Decision

15. The decision MUST be a function of the spec, the current observations, the declarations, the previous route, the time each member was last confirmed, the current time, the time the controller began to poll peers, and the peers read since then. Checked by unit tests on that function.
16. An observation of a member whose site is not known MUST count as `Unknown`, whatever was last observed. It MUST NOT count as writable. A site is known when it is the local site, or a peer whose document is fresh ([RFC#0004]).
17. In both modes, if a member is `Unknown`, it MUST stay in the route only while it was in the previous route and `now - lastConfirmed < unknownHold`.
18. `Single` mode MUST route to the member chosen by this table, checked in order. The first row that matches decides.

| # | Condition | Route | Reason |
|---|---|---|---|
| 1 | Two known sites declare different primaries, or the local site's workloads do ([RFC#0003]). | Nowhere | `DeclarationsDisagree` |
| 2 | Two or more members are writable, and the policy is `PreferDeclaredIfConsistent`, and every site with a member declares the same primary, and that member is writable. | The declared member | `PreferDeclared` |
| 3 | Two or more members are writable. | Nowhere | `MultipleWritable` |
| 4 | Exactly one member is writable, and a known site declares another member. | Nowhere | `NotDeclared` |
| 5 | Exactly one member is writable. | That member | `Active` |
| 6 | A member is `Transitioning`. | Nowhere | `Transitioning` |
| 7 | The previous route's member is `Unknown` and within its hold. | The previous member | `HeldUnknown` |
| 8 | The previous route's member is `Unknown` and past its hold. | Nowhere | `UnknownTimeout` |
| 9 | A member is `Unknown`. | Nowhere | `MemberUnknown` |
| 10 | Otherwise. | Nowhere | `NoEligibleMember` |

A member is writable when it is `Stable`, eligible, and has role `primary`. A site that declares no primary takes no part in rows 1 and 4, and fails the "every site" test of row 2.

19. `Set` mode MUST route to every member that is `Stable` and eligible, filtered by locality:

| Locality | Route |
|---|---|
| `LocalFirst` | Local eligible members if there is one, else every eligible member. |
| `LocalOnly` | Local eligible members only. |
| `Any` | Every eligible member. |

20. In `Set` mode, a member in the previous route that is now `Transitioning` MUST stay in the route, unless the locality filter excludes it. A member in the previous route that is now `Unknown` follows requirement 17. `LocalFirst` prefers the local site only while it has a `Stable`, eligible member.

| `Set` route | Reason |
|---|---|
| At least one member that is not held | `Eligible` |
| Only held members | `HeldUnknown` |
| Nowhere, and a previously routed member is past its hold | `UnknownTimeout` |
| Nowhere, otherwise | `NoEligibleMember` |

21. Declarations and the `multiple` policy MUST NOT affect `Set` mode.
22. In `Single` mode, the controller MUST raise a Warning event and set the `Multiple` condition when two or more members are writable, whatever the policy.
23. The controller MUST expose the route and the conditions as metrics, read from the status at scrape time, so a route to nowhere can raise an alert.

## Status

24. `status.route` MUST show the routed members, the reason, and the time the route last changed.
25. `status.members` MUST show, per member: site, role, eligible, state, reason, the observation time, and the last time it was confirmed. For a routed member with endpoints, it MUST show the path, as in the Endpoints table.
26. `status.declarations` MUST show each known site's declared primary.
27. The `Routed` condition MUST be `True` when the Service has at least one endpoint and no other owner holds it, and `False` otherwise. Its reason MUST follow this table, first match first. Checked by the unit tests `TestRoutedCondition` and `TestServiceConflict`.

| # | When | Reason |
|---|---|---|
| 1 | Another owner holds the Service (requirement 9). | `ServiceConflict` |
| 2 | The Service has no endpoint, and the decision routes to a member. | `NoEndpoints` |
| 3 | Otherwise. | The decision's reason |

28. `status.observedGeneration` MUST be the `metadata.generation` that the status was computed from.

## Startup hold

29. `spec.policy.startupHold` MUST be between 0s and 10m, and MAY be more than 0s only in `Single` mode. Unset or 0s turns the hold off.
30. The hold MUST last while all of these are true: `startupHold` is more than 0s; less than `startupHold` has passed since the elected controller began to poll peers; and a site that hosts a member, other than the local site, has not had a document read since then ([RFC#0004]).
31. While the hold lasts, the controller MUST NOT route to a local member. Where requirement 18 picks a local member, the route MUST be nowhere, with reason `AwaitingPeers`. A route to a remote member MUST NOT change.
32. The controller MUST keep the time it began to poll, and the peers read since then, in memory only, so that every start begins a new hold.

## Status at startup

33. The reason that status gives for the route MUST be `AwaitingPeers` while all of these are true: the elected controller's first poll of every peer since it began to poll has not ended, whether each poll read a document or failed ([RFC#0004]), where a `pollInterval` of 0s polls nothing and so has no first poll to wait for; a site that hosts a member, other than the local site, has not had a document read since then; and, when `startupHold` is more than 0s, less than `startupHold` has passed since then. This holds in both modes. It applies to `status.route.reason`, and to the reason of the `Routed` condition wherever that reason is the decision's. `status.route.message` MUST name the sites not read yet, and give the decision's reason and message. Afterwards, status MUST give the decision's reason.
34. Requirement 33 MUST NOT change the route or the endpoints. `status.route.members`, `status.route.endpoints` and the status of the `Routed` condition MUST show what the controller writes, as requirements 24 and 27 say.

## Applying a decision

35. The controller MUST apply each decision in this order, and MUST stop at the first read or write that fails:
    1. delete every EndpointSlice of the application name that is not the slice of a routed member with endpoints, and every one on a Service conflict (requirement 9);
    2. write the `Export`s and `Import`s, then the Service;
    3. write the EndpointSlice of each routed member with endpoints.

    When the controller cannot read where a routed member takes traffic, step 1 MUST keep the EndpointSlices of every routed member.
36. In `Single` mode, the application name's EndpointSlices MUST NOT name two members at once, also when a write fails. Checked by a unit test that fails each write of a route change in turn, and by the end-to-end `switch` step.
37. An EndpointSlice that the controller wrote MUST count as in place until the controller deletes it, also while the controller's cache does not show it.
38. The previous route (requirement 15) MUST be the members of the controller's last decision, kept in memory. After the controller starts, it MUST be the members of `status.route` that have an EndpointSlice in place.
39. The controller MUST write status after each decision, also when a step of requirement 35 failed. `status.route.members` MUST hold the decision's members, less each member with endpoints whose EndpointSlice is not in place. On a Service conflict, it MUST hold the decision's members, since no EndpointSlice is to be written. `status.route.endpoints`, the `Routed` condition and `status.members[].path` MUST show the EndpointSlices in place.
40. The `Applied` condition MUST be `True` with reason `Synced` when every step of requirement 35 succeeded, and `False` with reason `SyncFailed` and the error as its message otherwise.
41. A failure after the decision MUST NOT delay the next decision. It MUST come within 2s, or when a hold ends if that is sooner.

# Design

## Inputs

| Input | Source |
|---|---|
| Local members' observations | The plugin, on every reconcile ([RFC#0003]). |
| Remote members' observations | The peer's last fresh document ([RFC#0004]). |
| Declarations | The local plugin for the local site. Each peer's document for that peer. |
| Previous route | The last decision, in memory. After a start, the members of `status.route` that have an EndpointSlice: status can be older than the last decision when a status write failed, and a slice can outlive the decision that dropped it when its delete failed. |
| Last confirmed times | `status.members`. They survive a controller restart. |

## States and roles

| State | Meaning |
|---|---|
| `Stable` | The plugin read the member, and the member is not moving. |
| `Transitioning` | The member is moving: a switchover, a promotion or a demotion is in progress. |
| `Unknown` | The plugin could not read the member, or the peer that hosts it is unreachable. |

| Role | Meaning |
|---|---|
| `primary` | Accepts writes. |
| `replica` | Read-only. |
| `unknown` | Not known. |

## Why a partition does not stop the local primary

At site A, during a partition from site B, A's primary is `Stable` and writable, and B's members are `Unknown`. Row 5 routes A to its primary. Row 3 cannot match, since an `Unknown` member never counts as writable. If the operator promotes B's member during the partition, both sites route to their own primary until the partition heals. Then each site sees the other's declaration, which differs from its own, and row 1 routes both nowhere. Row 3 would route them nowhere too. Strait cannot detect a second primary it cannot see. Requiring every site to be known before routing would stop every site whenever one link fails, which turns a partition into an outage everywhere.

## Why the startup hold is opt-in and narrow

| Choice | Reason |
|---|---|
| Off unless set. | A controller that restarts during a real partition stops its local primary for up to `startupHold`. Off, the behaviour is the one above. |
| It counts from the controller's start, not from a link failure. | A partition that begins while the controller runs is handled as above. Only a controller that starts knows nothing of what the other sites declare. |
| Only a local member is held. | The risk is a local primary that the other sites have abandoned. A remote member is routed only from its site's document, or within `unknownHold` of its last confirmation. |
| It ends after `startupHold`, at most 10m. | Peers that stay unreachable are a partition. The site then routes as above. |
| `Single` mode only. | `Set` mode routes to followers and ignores declarations (requirement 21). |

## Why status at startup says `AwaitingPeers`

| Choice | Reason |
|---|---|
| The reason changes, the route does not. | Routing at startup is as above, and `startupHold` is the opt-in that changes it. A status that showed nowhere while the endpoints point at a member would read as safe when it is not. |
| It lasts until the first poll of every peer has ended, read or failed. | Before that poll, the controller cannot tell a peer that answers from one that does not. After it, the decision shows a peer that did not answer: its members are `Unknown`, with reasons such as `HeldUnknown` or `UnknownTimeout`. |
| It does not wait for a peer that stays unreachable. | A surviving site whose controller restarts while another site is lost routes its local member, and a status reader that waits for `Active` sees it once the first poll has failed. |
| With `startupHold`, it ends at the latest when the hold ends. | The hold is the operator's bound on how long a start changes what the site shows. |
| Both modes. | The rule is about what the controller has polled, not about which members it routes. |

What `status.route` shows after a site comes back:

| When | `status.route` |
|---|---|
| Before a controller is elected | What the previous controller wrote. See [Limitations](#limitations). |
| From the elected controller's first decision until its first poll of every peer has ended, or until `startupHold` ends if that comes first | Reason `AwaitingPeers`. Members and endpoints: what the controller writes. |
| Afterwards | The decision's reason. A peer that did not answer shows as `Unknown` members. |

## Why `Single` declarations matter

A declaration is the operator's intent. Rows 1 and 4 refuse to route when intent and observation disagree. During a correct switchover from A to B, the sequence is:

| Step | A declares | B declares | Writable | Route |
|---|---|---|---|---|
| Before | `pg-a` | `pg-a` | `pg-a` | `pg-a` (row 5) |
| A is demoted | `pg-b` | `pg-a` | none | Nowhere (row 1) |
| B is told to promote | `pg-b` | `pg-b` | none, `pg-b` is `Transitioning` | Nowhere (row 6) |
| B is promoted | `pg-b` | `pg-b` | `pg-b` | `pg-b` (row 5) |

## Applying a decision

Requirement 35 deletes before it writes, so a route change passes through nowhere, and a failure leaves no member that the decision dropped.

| Failure | Left in place |
|---|---|
| A delete, in step 1 | Each slice not deleted yet. No slice is written, so no member joins the route. |
| Reading the routed members' targets or the Service, or a write in step 2 | The routed members' slices as they were. Every other slice is deleted. |
| A slice write, in step 3 | The slices written before it, and the other routed members' slices as they were. |

In each case `Applied` is `False` with the error, status shows what is in place (requirement 39), and the next decision tries again.

## Route changes and connections

| What | After a route change |
|---|---|
| The application name's EndpointSlices | Rewritten. Strait changes nothing else: not the client, not the member, not the CNI's state. |
| An established connection | Not moved and not closed. It stays on the member it reached until the client or the member closes it. |
| A new connection | Follows the new endpoints, as the CNI resolves the Service. |
| A new connection, where the CNI translates Service traffic per packet with connection tracking | It can match a stale tracking entry and reach the previous member, while that member is still a backend of any Service. Example: Cilium whose socket load balancing does not cover pods. |

Socket load balancing that covers pods picks the backend when the client connects. For Cilium, that is socket LB on with `socketLB.hostNamespaceOnly=false`, which the agent reads as `bpf-lb-sock-hostns-only: false`. A provider or another chart value can set it to true, so read the agent's configuration.

A client must not rely on a route change to stop its traffic to a demoted member. Only the member can refuse it, as a demoted database refuses writes.

What the two-site test showed, at the site with socket LB in the host namespace only:

| Fact | Status |
|---|---|
| 15 new connections reached the old backend over 2 hours. | Observed |
| Cilium's service connection tracking entries for the application ClusterIP still named the old backend. They were non-closing, with a long lifetime. Three of them were refreshed at the times of the misrouted connections. | Observed |
| New connections that reused a client source port matched those entries and reached that backend. | Inferred |
| The old backend was still a backend of other Services: the database operator's own read and read-write Services, and Strait's `Export` for replication. | Observed |
| The other site ran socket LB that covers pods, and saw no such connection. | Observed |
| Those entries are the cause, and socket LB that covers pods prevents it. | Inferred, not proven by a dedicated test |
| Writes stayed safe only because the demoted member refused them. Reads would have reached the replica. | Observed for writes, inferred for reads |

## Endpoints

| Active member | Path | EndpointSlice |
|---|---|---|
| Local | `Local` | One slice per member. Addresses: the ready endpoints of the member's endpoint Service. Port: that Service's target port. |
| Remote, through the gateway | `Gateway` | One slice per member. Addresses: the active gateway pod. Port: the member's `Import` gateway port. |
| Remote, endpoint-direct | `EndpointDirect` | One slice per member. Addresses and port: the member's own, from the peer's document. |

One slice per member, because an EndpointSlice carries one set of ports and members differ in port.

The controller creates one `Export` for each local member and one `Import` for each remote member, named `<siteservice>-<member>` and owned by the `SiteService`. The same name at every site lets an `Import` find the peer's `Export` without more configuration.

## Metrics

| Metric | Labels | Value |
|---|---|---|
| `strait_siteservice_endpoints` | namespace, siteservice | Endpoints written. 0 is a route to nowhere. |
| `strait_siteservice_route_reason` | namespace, siteservice, reason | 1 for the current reason. |
| `strait_siteservice_condition` | namespace, siteservice, condition | 1 while the condition is True. |
| `strait_peer_reachable` | peer | 1 while the peer's document is fresh ([RFC#0004]). |
| `strait_link_healthy`, `strait_link_active` | link, peer, transport | From `SiteLink.status` ([RFC#0005]). |

## Conditions and events

| Condition | True when |
|---|---|
| `Routed` | The Service has at least one endpoint. |
| `Multiple` | Two or more members are writable. |
| `DeclarationsDisagree` | Two known sites declare different primaries, or the local site's workloads do. |
| `Held` | The route keeps an `Unknown` member within its hold. |
| `Applied` | Every read and write of the last decision succeeded. |

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| One port per `SiteService`. | A dependency that needs two ports at once. |
| `PerMember` mode is not served. | A client-routed system such as Kafka or Valkey Cluster. |
| A second primary hidden behind a partition is not detected until the partition heals. | None. Detecting it needs a quorum, which is the workload's job. |
| The startup hold and the status at startup begin at the controller's first decision. Until then, the EndpointSlices and the status that the previous controller wrote stay in place. A site that comes back serves its old route, and shows its old status, until the new controller decides. That takes the controller pod's start, plus the leader election's lease, 15s, when the previous controller did not release it, as after a crash ([RFC#0004]). In the end-to-end test, with the image on the node, the new controller decided 1s after the old pod was deleted. | A site that must not serve at all between its return and the controller's first decision, or a status reader that must tell an old status from a new one. |
| The startup hold covers a controller that starts. A controller that was frozen with its node and resumes keeps its memory of the peers it read, so it is not held. It reads them again within one `pollInterval`. | A platform that freezes nodes for long, such as live migration. |
| Members of one `SiteService` use one plugin. | A dependency observed by two plugins. |
| A route change does not stop new connections to the previous member while the CNI's connection tracking still names it and it is a backend of any Service. Strait owns no CNI state ([RFC#0001]). | A CNI that offers a supported way to drop the tracking of one Service backend. |
| A remote site learns of a demotion through the exchange, so for up to `peerTimeout` ([RFC#0004]) it may still route to a member that its own site has just demoted. Writes in that window reach a read-only database and fail. | A workload whose clients cannot retry a failed write. |
| After a controller start, a routed member with no EndpointSlice, as when it had no endpoint, is not in the previous route. It is not held while `Unknown`, and routes nowhere until it is confirmed again. | A hold that must survive a restart for a member with no endpoint. |
| The status refreshes member timestamps at most every 10s while nothing else changes. After a controller restart, a hold starts from the last written time, so it can end up to 10s early. The early end routes nowhere, never to a guess. | Holds shorter than 10s that must survive a restart exactly. |
